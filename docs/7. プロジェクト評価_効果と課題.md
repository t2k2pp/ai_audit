## 3. 課題

優先度は「高: 利用者の結果の正しさや導入可否に直結する」「中: 品質・保守性に影響する」「低: 改善余地」の 3 段階としています（本書作成者の判断）。

### 3.1 検証・品質保証

| # | 課題 | 詳細 | 優先度 |
|---|---|---|---|
| I1 | **実 LLM での品質が未確認** | v0.4 の全機能はダミーサーバでのみ検証。想定モデル（Qwen3.8-Flash-Next 等）でのプロンプト調整、特に compact ティアでの JSON 出力の安定性が未確認（tasklist.md 残課題） | 高 |
| I2 | **推論サーバ API の実機確認が未実施** | llama.cpp `/props`・`/tokenize`、vLLM `/v1/models`・`/tokenize`、Ollama `/api/show` の応答形式は設計書でも「未検証」としている。Ollama は `num_ctx` とモデル最大値の不一致リスクがある | 高 |
| I3 | **Windows / macOS バイナリと VSCode 上の動作が未確認** | Linux 版バイナリのみ動作確認済み。VSCode 拡張は TypeScript のコンパイル確認のみ | 高 |
| I4 | **効果の定量評価がない** | 根拠の有効率・カバレッジは `coverage.json` に出るが、v0.3 との比較や監査の誤検知率など、効果を示す数値を取得していない | 中 |
| I5 | **実機スモークテストが未実装** | 設計書 12 章の `AI_AUDIT_LIVE_TEST=1` による実機テストはコード上に存在しない | 中 |
| I6 | **CI がない** | `.github/workflows` がなく、テスト・TypeScript コンパイル・VSIX ビルドはすべて手動 | 中 |
| I7 | **VSCode 拡張のテストがない** | `extension.ts`（1,389 行・20 コマンド）が単一ファイルで、自動テストがない | 中 |
| I8 | カバレッジの低い箇所 | `core/config.py` 44%（設定の対話・保存）、`render/mermaid.py` 77%、`usecases/design_doc/facts.py` 77%、`index/parsers/javascript.py` 79% | 低 |

### 3.2 設計・機能上の制約

| # | 課題 | 詳細 | 優先度 |
|---|---|---|---|
| I9 | **呼び出し解決が名前ベースの近似** | 型推論をしないため、同名メソッドは `ambiguous` 扱いになる（`index/graph.py`）。監査の文脈同梱や設計書の関連ソース抽出の精度に影響する可能性がある | 中 |
| I10 | **大規模リポジトリでの処理時間が未計測** | ファイル単位の要約で LLM 呼び出し数はファイル数に比例する。`LLM_PARALLEL` で並列化できるが、実際の所要時間・推論サーバ負荷は未計測 | 中 |
| I11 | 目次がテンプレート固定 | 小さいモデルでの安定性を優先して LLM による目次生成をやめたため（design.md 実装判断ログ）、プロジェクトの性質に合わない章構成になる可能性がある | 低 |
| I12 | v0.3 からの移行コスト | ChromaDB 廃止により v0.3 で蓄積した設計思想データは再抽出が必要（設計書 8 章） | 低 |
| I13 | 思考モードの制御方法が未確認 | `LLM_REASONING` / `LLM_EXTRA_BODY` で汎用的に渡す設計だが、想定モデルでの API 制御方法は未確認（設計書 1.3） | 低 |
